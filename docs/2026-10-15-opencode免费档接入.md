## 上游端点

`https://opencode.ai/inference/v1/chat/completions` 与 `/v1/responses`，
标准 OpenAI 兼容，鉴权用**匿名公开凭据** `Bearer public`（不是用户自己的 OAuth token；
拿 OAuth 打这个端点反而会 403）。

## 免费档闸门：2026-10-14 起的全部通过条件（逐项实测）

报错文案只说「只能在 OpenCode 内使用」、不指出缺哪一项，所以每条都记下来：

| # | 条件 | 不满足时 |
|---|---|---|
| 1 | 必须 `stream: true` | 403 FreeTierError |
| 2 | 必须带官方 5 个核心工具 `shell/edit/glob/grep/read`，且 description 与 parameters **逐字节等于官方 CLI 定义** | 403 |
| 3 | 四个会话头同值：`x-opencode-session` / `x-opencode-session-id` / `x-session-affinity` / `X-Session-Id` | 403 |
| 4 | 会话 id 必须是官方 `Identifier.descending()` 布局：`ses_` + 12 位**降序毫秒时间戳** hex + 14 位 Base62 | 403（随机 hex 即使形状对也拒） |
| 5 | `x-opencode-project` 必须是**裸 40 位小写 hex**；官方 `prj_*` 规范 id 反而被拒 | 403 |
| 6 | **不能发** `x-opencode-request` | 403 |
| 7 | UA 形状 `opencode/latest/<ver>/cli`；`Authorization` 大小写敏感的字面量 `Bearer public` | 401/403 |

逆向依据：`jasonxu114514/opencode2api`（Go，★651，当日仍在更新）的
`internal/gateway/upstream.go`、`internal/identity/request.go`，
以及内嵌的 `internal/gateway/opencode_tools.json`（官方工具真定义，已存为
`hub-go/assets/opencode_tools.json`）。

另一份参考 `bigdata2211it-web/opencode-free-proxy` 是 2026-05 的，模型名与 UA
都已过时，只能证明「这条路存在」。

## 协议支持面是按模型互补的（逐个实测）

上游对每个模型只放开一种协议，两边正好互补：

- **8 个只收 chat**：`cat-jam-free` `longcat-2.5-preview-free` `space-bunny-free`
  `mimo-v2.6-flash-free` `step-5-preview-free` `deepseek-v4.1-flash-free`
  `nemotron-3.5-lightning-free` `big-pickle`
- **1 个只收 responses**：`muse-spark-1.3-contributor-free`

打错协议上游回 `ModelProtocolUnsupported`。线路在本地就按 `NoChat`/`NoResp`
拦下来，给出「请走另一条路径」的可读提示，而不是把上游那句原话透出去。

## 交付内容

### 新线路 `oc`（:8800）

- `hub-go/opencode_proxy.go`：线路本体。`/v1/models`（带免费与上下文标注）、
  `/v1/chat/completions`（强制流式 + 补官方核心工具；客户端要非流式则收流再聚合）、
  `/v1/responses`（直通 + 非流式聚合）。会话 id 按请求内容做**稳定映射**，
  命中上游 prompt cache 亲和。
- `hub-go/assets/opencode_tools.json`：官方工具真定义（`//go:embed` 已在
  codex_catalog.go 的 `all:assets` 里覆盖，无需新增 embed 变量）。
- `hub-go/opencode_proxy_test.go`：15 个离线单测（会话 id 布局与稳定性、
  项目 id 形状、免费档闸门两形态、核心工具用真定义而非 stub、
  客户端同名工具被替换、目录元数据、协议双向守卫、上下文标注格式、
  只挂免费模型的拒绝路径）。

### 注册点（照 trae 的约定逐个补齐）

### 两个容易漏的集成点（已修并验证）

1. `scripts/aihub-switch.sh` 的自动探测表**原本没有 8800** → 重启 aihub 后
   `oc` 不会自动恢复，直连 :8800 的 DSH provider 会莫名失联。加上后实测
   切换输出已出现 `oc=✓`、监听表含 `:8800`。
2. `apiStopAll` / `apiExit` 原本不枚举 `oc` → 点「全部停止」后 :8800 仍留监听。
   已补。

### DSH 侧

`~/.dsh/profiles/web/cordis.patch.yml`（**改前已备份**
`cordis.patch.yml.bak-20261015-200736`）新增两个 provider：

- `aihub-oc` → `api: openai-completions`，`baseURL: http://127.0.0.1:8800/v1`，8 个模型
- `aihub-oc-resp` → `api: openai-responses`，同 baseURL，muse-spark

每个模型都写了 `name`（含「免费」+ 上下文）、`contextWindow`、`maxTokens`、`input`。

**刻意不碰聚合白名单 `agg_models.json`** —— 用户此前明确说过
「我是让你加进去候选单里面，没让你给我主动加到聚合端口」。要进聚合口请他在控制台自行操作。

## 需要用户做的事

1. **重启 dsh 才会加载新 provider**（profile 配置在启动时读）。
   我没有动承载本会话的进程，命令由你执行：退出当前 dsh 后重新进入即可。
   「热加载能否生效」这条我没验证。
2. `oc` 线路目前是**手动启动**（和其它线路一样默认不自动拉起）。要开机常驻，
   用 `AIHUB_LINES="dom intl qoder oc"` 启动，或在控制台点。
3. 免费档没有倍率概念，若你要把它们也挂进聚合口 `:8790`（给 Codex 用），
   请在控制台自行添加 `oc.<模型>`。
