## 四、发现的问题（不影响接手，建议后续处理）

1. **`/api/gateway` 端点返回的是 cc-switch/Hub Switch 时代的语义**：
   实测 `{"attached": false, "mode": "direct", "up": false, "port": 15721, "stack_enabled": false}`。
   方案 C 后 hub-go 自己就是网关（`:8790` 已 `up`），该端口的字段会让人误判"网关没起来"。
   建议改名为 `/api/gateway-legacy` 或改返回 `:8790` 的真实状态。

2. **`codex_catalog.go` 的目录模板依赖 cc-switch 时代产物**：
   `catalogTemplate()` 读 `~/.codex/cc-switch-model-catalog.json` 作为条目模板（克隆它保证 33 键齐全）。
   该文件当前存在（374857 bytes），但它是**外部依赖**——一旦被清理，桌面版模型目录就生成不了
   （CLI 不受影响，代码里有明确提示）。建议把模板内联进仓库（`hub-go/assets/` 已有目录）。

3. **`~/.codex/config.toml` 里有 cc-switch 遗留死段**：
   `[model_providers.custom]`（`base_url = http://127.0.0.1:15721/v1`，`experimental_bearer_token = "PROXY_MANAGED"`）
   仍在文件里，但顶层 `model_provider` 指向 `aihub`，该段不生效。无害，但会误导排障。

4. **思考模型 + 小 `max_tokens` 会返回空正文**（非 bug，但易误判）：
   实测 `dom.glm-5.3-flash` / `ccs-intl/hy4-preview` 在 `max_tokens=64` 时 `content=None`、
   `finish_reason=length`（思考 token 吃满），放到 800 即正常出正文。
   上游行为；客户端配小 max_tokens 时会看到"空回复"。

5. **线路未启动时报错清晰**（设计如此，非问题）：
   `:8790` 请求未启动线路的模型返回 HTTP 503 `line_not_running`，提示"请先在 AIHub 控制台启动它"。
   本次为验证 Chat 协议临时启动了 intl 线路（`:8799`，现已运行）。

## 用户反馈的三个新问题

## 根因（读 DSH 解析器确认）


- 原 `aggOpenAIModels` 只输出 `id`=英文 slug + `name`="slug · 倍率"，

# 2026-10-15 三次追加：DSH「选择要添加的模型」弹窗为何仍是 slug

## 现象

用户在 DSH 设置-模型页点「获取可用模型」，弹窗「选择要添加的模型」里
列的仍是 `intl.deepseek-v4.1-flash` 这种 slug，不是中文名。

## 根因（DSH 客户端行为，非 hub-go 问题）

弹窗来自 `@deepseek-ai/dsh-client-ui-settings-models/lib/client.js`：

```js
// client.js:874-877
children: (0, react_jsx_runtime.jsx)("span", {
    className: ModelsSection_module_css_default["candidateId"],
    title: candidate.name ?? candidate.id,   // name 只进悬停提示
    children: candidate.id                   // 可见文本硬编码用 id
})
```

**可见文本硬编码 `candidate.id`，`name` 只放在 `title` 悬停提示里。**
这是 DSH 客户端的渲染选择，hub-go 侧无法通过改 `/v1/models` 绕过
（除非把 `id` 本身改成中文，但那会让请求的 model 字段跟着变，破坏路由）。

## 关键佐证：弹窗列表 = `/v1/models` 的 id 全集

截图里弹窗的 10 个可见项（前 10，其余被滚动条截断）与 `:8790/v1/models`
返回的 `id` **逐个一致、顺序一致**，确认弹窗数据源就是网关目录。

## 好消息：添加后就有中文名

`adopt()` 会把 `name` 一并存进配置（client.js:574-582）：

```js
function adopt(candidate) {
    return {
        id: candidate.id,
        ...candidate.name === void 0 ? {} : { name: candidate.name },      // ← 中文名被保存
        ...candidate.contextWindow === void 0 ? {} : { contextWindow: ... },
        ...candidate.maxTokens === void 0 ? {} : { maxTokens: ... },
    };
}
```

所以：**弹窗勾选时显示 slug（接受），添加进 `cordis.patch.yml` 后，
模型选择器/列表会显示中文名 + 上下文 + 输出上限。**

## 用户决策

选「不改，接受弹窗显示 slug」。理由：`id` 是请求时真实使用的模型名，
改成中文会让 Codex/Claude 存量配置全部失效。

# 2026-10-15 五次追加：502 故障根因与根治

## 用户报障

Codex 使用国际版 `deepseek-v4.1-flash` 报：
```
unexpected status 502 Bad Gateway: upstream error:
Post "https://www.workbuddy.ai/v2/chat/completions":
proxyconnect tcp: dial tcp 127.0.0.1:43345: connect: connection refused
```

## 根因（完整链条，逐步取证）

1. **死代理**：`43345` 未监听（`ss -ltn` 无该端口）。
2. **进程环境固化了死代理**：`/proc/<aihub>/environ` 里
   `https_proxy=http://127.0.0.1:43345` —— 这是**进程启动时**继承的。
3. **为什么会继承**：`scripts/start.sh` 第 21-27 行**故意**把 shell 的
   `HTTP_PROXY/HTTPS_PROXY/...` 用 `--setenv` 带进 systemd 用户服务
   （注释：「国际线路要 VPN/代理出网」，设计意图正确）。
   我那次 `aihub-switch.sh` 是在代理已失效的 shell 里跑的，死端口被固化。
4. **为什么 no_proxy 没救**：`no_proxy=localhost,127.0.0.1,::1,[::1]`
   不含 `www.workbuddy.ai`，所以后端请求全走该代理。
5. **为什么 dom 线路没事**：`proxy_cn.go:39` 是 `DirectOnly: true`，
   `proxy.go:155` 走 `directClient()`（忽略一切代理）。**intl 没有这个保护**。

**复现确认**：修复前 `intl` 100% 不可用（直连 `:8799` 也返回同样的 502）。

## 根治（不是绕过）

改 `hub-go/proxy_util.go` 的 `newBackendClient()`：
代理地址在**使用前先做 TCP 可达性探测**，不可达就返回 `nil`（= 直连）。

```go
Proxy: func(req *http.Request) (*url.URL, error) {
    if u, _ := http.ProxyFromEnvironment(req); u != nil {
        if proxyReachable(u) { return u, nil }
        return nil, nil // 代理死了：直连
    }
    u := systemProxy(req)
    if u != nil && !proxyReachable(u) { return nil, nil }
    return u, nil
},
```

`proxyReachable()` 带 **30 秒 TTL 缓存**：既避免每请求 TCP 握手，
又能在代理恢复/失效后**双向自愈**（永久缓存会让「代理后来起来了」也用不上）。
状态变化时才写 `hub.log`，不刷屏。
