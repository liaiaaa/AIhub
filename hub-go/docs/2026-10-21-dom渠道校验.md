# 2026-10-21 国内版渠道校验（11128）

## 症状

2026-10-20 约 23:00 起，腾讯给 WorkBuddy 对话网关加了第三方客户端渠道校验，
国内线路（dom）对话请求整条失败：

```json
{
  "code": 11128,
  "msg": "Illegal API invocation from an unapproved channel",
  "displayMsg": {"zh": "请求被拦截，请重新发送"},
  "displayTips": {"zh": "这次调用没通过渠道校验，可能不是官方客户端发出的。请用官方版本重新发送。"}
}
```

日志里 `msgs=2` 的会话标题请求能过、`msgs=23` 的真实对话被拦——**同一秒、同一凭证**。

## 与国际版 2026-10-16 那次的区别

| | 2026-10-16（intl） | 2026-10-21（dom） |
|---|---|---|
| msg | `conversation id missing` | `Illegal API invocation from an unapproved channel` |
| 缺什么 | 只是四个会话 id 头 | **整套请求指纹** |
| 解法 | `withConversationHeaders` 补四头 | 整体伪装官方内置 CLI |

所以 dom 不能照抄 intl 的补法，只补会话四头仍然被拦。

## 排查过程（走过的弯路）

1. 先按「间歇性风控」处理：加内部静默重试（`bf3cd08`）。**失败**——重试 3 次仍全被拦，
   说明是稳定的策略拦截，不是抖动。
2. 逐个排除假设，全部不成立：请求体大小、ACP 标记文本、system prompt 长度
   （28 字符 → 36K 字符都通过）、并发、tool_calls 链、tools 定义、22 条多轮。
   **教训**：自己在测试里构造的请求永远复现不了真实失败，因为真实失败取决于
   请求的**整体指纹**，而不是某个可枚举的字段。
3. 用户直接指出根因（腾讯 10-20 23:00 加渠道校验），转向「对齐官方客户端」。

## 对齐依据

`yreidev/workbuddy2api-panel`（GitHub）的 `docs/official-client.md`。该仓库
2026-10-20 从官网下载国内版 WorkBuddy 5.8.3 / 国际版 5.8.4（macOS arm64）
安装包，只解包阅读，记录了：

- 内置 CLI：`@tencent-ai/codebuddy-code` 2.161.0（`app.asar.unpacked/cli/`）
- 桌面端后台服务：`app.asar` 里的 `main/`

  `UserAgentHttpInterceptor`、`CommonHeaderHttpInterceptor`、

## 官方对话请求的完整形态（国内版）

UA：`WorkBuddy/5.8.3 WorkBuddy/5.8.3 CLI/2.161.0`
（形态 `WorkBuddy/<版本> <应用名>/<版本> CLI/<cli>`）

| 类别 | 头 |
|---|---|
| 公共 | `Accept: application/json, text/plain, */*`、`Content-Type: application/json`、`Accept-Encoding: gzip, compress, deflate, br`、`X-Requested-With: XMLHttpRequest`、`X-Product: SaaS` |
| 认证 | `Authorization`、`X-User-Id`、企业号 `X-Enterprise-Id` + `X-Tenant-Id`、`X-Domain` |
| 对话专项 | `X-Agent-Intent: craft`、`X-Agent-Type: main`、`X-Agent-Purpose: conversation`、`X-IDE-Name: WorkBuddy`、`X-IDE-Type: WorkBuddy`、`X-IDE-Version: 5.8.3`、`X-Private-Data: "true"`（值带引号） |
| 会话 id | `X-Conversation-ID`（uuidv7 带连字符 36 位，整段对话不变）、`X-Conversation-Request-ID`（uuidv7 去连字符 32 位，每轮） |
| 消息 id | `X-Conversation-Message-ID` 与 `X-Request-ID` **同值**（同一个模型消息 id，每次调模型新生成） |
| 链路 | `traceparent`、`b3`、`X-B3-TraceId`、`X-B3-SpanId`、`X-B3-Sampled: 1` |

官方**不发**：`Origin`、`Referer`、`X-CodeBuddy-Request`、`X-Machine-ID`、`X-Session-ID`。

`X-Device-Id-List`（qimei36）在 macOS 版官方客户端拿不到（安装包里 `qimei-node`
只有 `package.json`、没有原生库），官方也不发，所以网关不发。

## 实现

- `Proxy.OfficialChatClient`（只在 dom 置位）
- `withConversationHeaders` 命中时改走 `officialChatHeaders`（proxy.go）
- `randUUIDv7` / `uuidv7Hex`（proxy_util.go）——**必须用 v7 不是 v4**，
  上游若要验 id 形状，随机 v4 会露馅
- 探活路径 `domProbeHeaders` 也走同一个 `withConversationHeaders`，
  自动同源升级，避免「推理能用、看板全红」

## 第二层：system prompt 里的客户端签名（真正的主因）

只对齐请求头**仍然被拦**（用户实测 + 我自己重试 3 次全失败）。拿到真实失败
载荷（`dom-dump-*`，25 条消息 / 52 tools / 110KB）后逐项剥离：

```
完整真实载荷                        ✗ 11128（3/3 稳定）
去掉 tools                          ✗ 11128
去掉 stream_options                 ✗ 11128
去掉 reasoning_effort               ✗ 11128
max_completion_tokens→max_tokens    ✗ 11128
只留最后 2 条消息（不含 system）      ✅ 通过
system + 尾部 2 条                   ✗ 11128
```

触发点锁定在 **system 消息**。继续细分（每个配置重复 3 次，避开 429 干扰）：

| system 内容 | 结果 |
|---|---|
| 原 system（18943 字符） | 拦截 3/3 |
| 只留第 1 段「You are an AI agent powered by DeepSeek Harness.」（48 字符） | 拦截 3/3 |
| 去掉第 1 段 | 通过 2/2 |
| 「You are an AI agent.」 | 通过 2/2 |
| 「You are an AI agent powered by X.」 | 通过 2/2 |
| 「You are a helpful assistant powered by DeepSeek Harness.」 | 通过 2/2 |

**触发条件是完整短语 `You are an AI agent powered by DeepSeek Harness.`**，
不是单词黑名单——单独 "DeepSeek Harness" 不触发、单独 "You are an AI agent"
也不触发。上游靠客户端固定开场白识别第三方 harness。

### 已有同款机制，直接扩展

代码里 2026-10-10 就为 Codex 做过同类处理：`sanitizeHarnessPrompt`
（proxy_responses.go）把 "OpenAI" 写成 "Open AI"，因为当时 Codex 的
`OpenAI / Codex CLI / coding agent` 同现触发同一个 11128。所以这次**扩展
同一个函数**而不是另起一套：

```go
func sanitizeHarnessPrompt(s string) string {
	s = strings.ReplaceAll(s, "OpenAI", "Open AI")
	s = strings.ReplaceAll(s, "You are an AI agent powered by DeepSeek Harness.", "You are an AI agent.")
	return s
}
```

配套新增 `sanitizeHarnessMessages`（只处理 role=system 的字符串 content）。
**chat 路径此前从未清洗过**——2026-10-10 只修了 responses 路径，因为当时只有
Codex 在用 dom；dsh 走 `/v1/chat/completions`，所以这条路径补上。

替换成「You are an AI agent.」不丢语义：下游还有一段
「You are a coding agent powered by the <model> model.」承载产品信息。

### 为什么不改用户消息

签名只出现在系统提示词里。改写用户内容既越权，又可能弄脏模型看到的代码/
报错原文——那是推理要用的事实。

### 最终验证

那份之前稳定失败的同一份 dump（25 条消息 / 52 tools / 131KB，system 含签名），
经 hub 转发连续 3 次：**3/3 全部通过**。
