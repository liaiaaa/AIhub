# 2026-10-27 trae 流式卡顿排查（kimi-k3 等一分钟没消息）

> 用户报：用 aihub 反代的 trae `kimi-k3`，dsh 会话
> `session-ddd6042e-9832-4c9d-b2d6-da58434f6491` 等一分钟没有任何消息。

## 1. 事实链（全部实测）

| 时间 | 事件 |
|---|---|
| 11:33:27 | dsh 发出请求：`trae.kimi-k3`、6 条消息、74 个工具、payload **100KB** |
| 11:33:27 → 11:34:39 | dsh 侧**没有任何 assistant 事件**（会话里 71 秒空白） |
| 11:34:39 | 用户手动中止（`turn/end reason=aborted/user`） |
| 11:35:49 | hub 的 `converter-trae.log` 才记下 `◀ RESPONSE | 136.4s | think=405帧` |
| — | `usage.jsonl` 同一条：`in=21177, out=581, ms=141292` → **约 4.1 token/s** |

会话日志（`~/.dsh/sessions/--home-li-ai_projects-Operate~0020EasyEDA~0020Pro--/session-ddd6042e-.../session.v4.jsonl.zstd`）
里，`request/header` 之后直接跳到 71 秒后的 `assistant/attempt`（`stream: []`）——
dsh 在等待期间没拿到任何可渲染的帧。

## 2. 根因

1. **kimi-k3 是思考模型**：上游先吐一长串 `reasoning_content`，正文要等思考结束。
   实测同样 payload：`TTFB 17.4s`、首个正文 `27.5s`、共 30.2s（think 613 帧）。
   那次线上请求上游更慢：141s 只产出 581 token。
2. **agg 层没有缓冲**（排除的第一嫌疑）：`proxy_agg.go` 对 `kind=chat` 是
   `aggCall` 直调线路 handler；`usageTap` 也实现了 `Flush()`。经 :8790 的复现实验
   TTFB 3.3s、正文 15.0s、总 19.7s，说明 hub 能把帧实时送出去。
3. **hub 原先没有任何兜底**：
   - 上游静默就无限等，客户端也没有超时 → 表现成「卡死」；
   - dsh 71s 就 abort 了，hub 还把上游跑到 141s（`doChat` 用 `http.NewRequest`，
     没带请求 ctx）→ 白烧额度；
   - 日志只有总耗时，没有首帧耗时，事后无法区分「上游慢」和「hub 慢」。

## 3. 改动（`hub-go/trae_proxy.go`）

| 改动 | 作用 |
|---|---|
| `doChat` / `chatUpstream` 全部带 `ctx`（`http.NewRequestWithContext`） | 客户端断开时立刻中止上游 |
| `handleChat` 里 `ctx, cancel := context.WithCancel(r.Context())` | 一条链路一个 cancel，看门狗也能主动中止 |
| `streamToClient` 写失败即停（`clientGone()`），不再继续读上游 | 关页面 / Esc 后不再白烧额度 |
| 空闲看门狗：连续 `AIHUB_TRAE_IDLE_SECS`（默认 **120s**）没有任何帧 → 中止并回 `{"type":"upstream_timeout"}` 错误帧 + `[DONE]` | 上游卡死时客户端能看到明确原因，而不是无限等待 |
| 完成日志新增 `首帧=%.1fs | content=%d字节` | 下次判断「上游慢 vs hub 慢」一眼可见 |
| 非流式 `aggregateToClient` 也带 `ctx`，客户端走了不再回错误体 | 一致行为 |

## 4. 复现实验（同一份 payload，直接打上游）

| 路径 | TTFB | 首个正文 | 总耗时 |
|---|---|---|---|
| 直连 :8795（默认） | 17.4s | 27.5s | 30.2s |
| 经聚合 :8790（默认） | 3.3s | 15.0s | 19.7s |
| 直连 + `reasoning_effort: "low"` | 9.9s | 12.6s | **13.7s** |

`reasoning_effort` 上游接受（HTTP 200），单样本看能把思考压短；`thinking:{"type":"disabled"}`
**不生效**（仍产 118 个 think 帧）。样本各 1 次，不能当定论。

## 5. 客户端侧建议（需用户决定，未擅自改）

- dsh profile 里 `trae.kimi-k3` 目前只有 `id/name/input`，没有 `reasoningEfforts`。
  补上之后 dsh 会把它当推理模型（模型选择器出现思考档位，可发 `reasoning_effort`）；
  若不想改 profile，把默认模型换回 `qoder.DeepSeek-Flash` 更稳。
- 重活用 qoder/intl；trae 的 kimi-k3 更适合短对话——它的思考长度对 agent 负载不友好。

## 6. 提速：默认思考档位（2026-10-27 追加）

同一份 127KB 载荷（10 条消息 + 100 个工具），交替各跑两次：

| 请求 | TTFB | 首个正文 | 总耗时 | think 帧 |
|---|---|---|---|---|
| 默认 #1 | 2.8s | 10.7s | 14.4s | 156 |
| `reasoning_effort=low` #1 | 3.2s | 8.3s | **9.1s** | 286 |
| 默认 #2 | 2.2s | 19.8s | 20.2s | 1079 |
| `reasoning_effort=low` #2 | 2.0s | 3.1s | **4.4s** | 65 |

加上先前一次对照（30.2s vs 13.7s），三组都显示 **低档位明显更快（约 2–3 倍）**。
kimi-k3 的时间基本都花在 thinking 上。后续补测 `high` 两次（13.7s / 9.0s、think 帧 501/72）
也都 200 通过——样本方差太大（默认组 14.4s/20.2s/30.2s，think 帧 156/1079/613），
因此**不能**断言「low 一定更快」或「high 一定思考更久」；唯一确定的是上游默认不放水，
用户要的就是那个档位。

于是新增 `AIHUB_TRAE_EFFORT`：客户端没显式给 `reasoning_effort` 时注入该值（默认空 = 不注入，
保持上游默认）。日志 `▶ REQUEST` 行会带 `effort=low` 便于确认；客户端自己带了档位就不覆盖。

**2026-10-27 用户拍板：不用低档位，kimi-k3 就用最强思考**（降档会失去这个模型的意义）。
所以默认**不注入**——不设环境变量、数据根也不放 `trae_effort.txt` 时，hub 完全按上游默认走，
也就是用户实测到的「思考很久但想得深」。下面两种开关方式留给以后实验用：

1. 环境变量 `AIHUB_TRAE_EFFORT=low`；
2. **数据根放 `trae_effort.txt`，内容写 `low`**（与 `zcode_api_key.txt` 同一套约定）。
   桌面快捷方式启动带不了环境变量，用文件更省事；每个请求现读，**改完不用重启**。
   只接受 `low` / `medium` / `high`，其它值忽略（避免把错拼的档位发给上游）。
