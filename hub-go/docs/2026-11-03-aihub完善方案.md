- `lineKeys()` / `aggregatedLinePorts()` / `allLinePorts()`（`lines.go:48-74`）改读运行时表，**签名不变**，调用方零改动。

**后端 API**（`hub_api.go`，风格沿用现有 `{ok,msg}`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/lines` | `{lines:[{key,display,port,log,aggregated,risk,builtin,impl,enabled}], impls:[...]}`，`impls` 来自注册表，喂前端下拉 |
| POST | `/api/lines/add` | `{key,display,port,aggregated}`；校验 `^[a-z][a-z0-9]{1,15}$`、不重名、端口 1024-65535 且不与 `allLinePorts()`/8790/8801 冲突 |

| POST | `/api/lines/remove` | 内置拒绝；被 `last_lines` 或 `agg_models.json` 引用时 409 + `refs:{...}`，`force:true` 才连带清理 |

校验失败统一 **200 + `{ok:false,msg}`**，与现有 `apiLineStart`（`hub_api.go:117`）一致，避免前端 `act()` 分叉。

**前端**
- `page-lines` 工具条加「管理线路」→ 弹层：每行显示名/端口/聚合/实现/内置标记 + 停用/删除；底部「+ 新增线路」，实现方式下拉只列已注册 impls，并写明「新增一条**能真正转发**的线路仍需写 Go 适配器」。
- `SERVICES`（`console.html:811`）改为启动时拉 `/api/lines` 动态渲染（常量留 fallback）；`TestConsoleServicesMatchLineSpecs` 改成「内置 8 条 ⊆ 运行时清单且显示名一致」。
- 设置页加「线路与数据文件」只读区块：`lines.json` / `agg_models.json` / `state.json` 的体积、mtime、重置入口。

**迁移与兼容**
- `state.json.last_lines` 经 `sanitizeLineNames`（`hub.go:130`）按 `knownLineNames` 过滤，运行时表生效后自动跟随，**无需迁移脚本**（已复核）。
- 删线路时连带清 `agg_models.json` 里对应 slug（保留会让 `aggLinePort[line]` 缺失）。
- 内置 8 条 key 永不改，老 `state.json` 完全兼容。

**风险（硬边界，必须让用户知道）**
1. **转发实现不可配置化**：每条线路的 `Chat` 协议都不同（4 份 `streamToClient`），新增能用的线路必须写 Go 文件 + 在 `line_adapter.go:310` 登记一行。配置化只能到「元数据 + 占位 + 启停门面」。
2. `statusMap()`（`hub.go:711`）是逐线路手写分支，自定义线只能给通用 `{up,ok,detail}`。
3. 端口清扫 `sweepPorts` 依赖 `allLinePorts()`，动态端口必须在清扫前算好。
4. `lines_test.go` 四类断言（端口清单/顺序/dom 高风险/SERVICES 对齐）都要跟改。

### 3.2 客户端怎么读（关键结论）

- **DSH**：`dsh-llm-pi-ai` 的 `discoverModels`（index.js:2351-2352）只取 contextWindow/context_window/max_output_tokens；**档位来自 profile 里手写的 `models[].reasoningEfforts`**（本机 `~/.dsh/profiles/web/cordis.patch.yml:27/41/53…`），转成 `thinkingLevelMap`（index.js:586-606），发送时 `params.reasoning_effort = map[level] ?? level`。层级 = off/minimal/low/medium/high/xhigh/max。
  → **改 aihub 的 `/v1/models` 对 DSH 的档位菜单零影响**，真正的杠杆是**生成那份 YAML**。
- **Codex**：CLI 走 `/v1/responses`，aihub 读 `raw["reasoning"].effort` → `chatBody["reasoning_effort"]`（`proxy_responses.go:156-158`）；桌面目录 `codex_catalog.go:105-146` 只改 slug/name/priority/context，`supported_reasoning_levels` 与 `default_reasoning_level` **全部沿用模板** `assets/codex-catalog-template.json`（仅 1 条、low/high/max、default high）；CLI 的 `/v1/models`（`proxy_responses.go:60-107`）硬编码 low/medium/high/max、default **medium**。本机 `~/.codex/config.toml` 有 `model_reasoning_effort="max"`、`enabled-reasoning-efforts=[...]`。

### 3.3 统一方案

新增 `hub-go/line_efforts.go`：

```go
type lineEfforts struct{ Levels []string; Default string; CanDisable bool }

func (h *Hub) effortsOf(line, model string) (lineEfforts, bool)   // 唯一事实源
func canonicalToWireEffort(line, model, want string) (string, bool) // 规范档 → 线路档
func wireToCanonicalEffort(line, model, wire string) string         // 反向
```

- 规范档 = `minimal / low / medium / high / max`（与 DSH 层级、Codex 可显示名取交集；`xhigh` 仅线路原生支持时才宣告）。
- 映射：dom/intl/qoder/oc 恒等；zcode `{minimal→low, medium→high, xhigh→max}`；trae `{minimal/low→light, medium/high→high, max→extra_high}`（对外只宣告 low/high/max）；teleagent/mimo 不宣告。
- 未知档就近钳制（复用 `qoderEffortRank`）。

**三处出口同源**：`model_meta.go:193 metaJSON` 加 `efforts`；`proxy_agg.go:804` 输出 `reasoning:{efforts,default_effort}`；`proxy_responses.go:100` 改成按模型的 `codexReasoningLevels(line,model)`；`codex_catalog.go:105` 每条写自己的 `supported_reasoning_levels`。

### 3.4 现在就会选错的三处

1. **trae**：客户端发 `max`（Codex 目录里就有）→ 原样透传，上游不认（`trae_proxy.go:150-153` 客户端值直接放行、无钳制），静默降档。
2. **Codex** 对所有模型都显示 low/medium/high/max 且 default=medium，而 aihub 不发言时会注入 max → 菜单默认与实际行为不一致；qoder 某些模型没有 medium/high，选了只能靠钳制兜。
3. **DSH 配置已漂移**：`qoder.GLM-5.3-Flash`（真实 high/max）、`trae.kimi-k3` 都没写 `reasoningEfforts`，等于没得选。

### 3.5 风险

① 只改输出不改注入 → dom/intl 默认 max 不变（安全）；② trae 一旦宣告档位，客户端总会显式发值，**env / `trae_effort.txt` 的手动档位被永久压过**；③ Codex 桌面目录启动只读一次，改完须重写文件 + 重启，写错名字可能整表解码失败（2026-10-27 写空事故）；④ 给 mimo/teleagent 宣告档位是赌博（上游可能忽略或 400）。

## 5. 参考 magpie 接入 codex

### 5.1 magpie 的做法

- **单端口靠路径前缀分流**：`internal/gateway/oneport.go:29 clientPrefixes` = `/v1`、`/v1beta`、`/models`、`/responses`、`/messages`、`CodexPath`…，`ClientPath(p)`（`:43`）判定；`internal/gui/web.go:422-437 onePort(page)` 未命中交给页面、命中交给 `gw.Front()`；附带 `X-Magpie-Page-Port` 头把「经页面端口进来的请求」降级为外机、必须带 key。
- **Codex 三种接法**（`codex_backend.go:41` `CodexPath="/backend-api/codex"`）：a) 伪装 ChatGPT 后端保留登录态；b) `base_url=<gw>/v1` + `model_catalog_url=<gw>/v1/codex/models`（`codex_catalog.go:22`，注释原文：「`/v1/models` stays OpenAI's list, which Codex can't read」）；c) 本机 `model_catalog_json` 本地文件 —— **aihub 现在走的是 c**。
- 端点双注册 `/v1/responses` 与 `/responses`；`previous_response_id` 由 `prev_response.go` 内存保存（6h / 256MiB / 按 key 分 scope）；压缩走 `/responses/compact`；`fallback.go:1653 retryable()` 里上下文溢出**不可换线**。

### 5.2 aihub 该做什么

| 项 | 判断 | 工作量 |
|---|---|---|
| 补 `/v1/models` 字段（§4.1） | **做** | 0.5 |
| Codex 目录 per-model 化（§4.2） | **做** | 0.5 |
| `GET /v1/codex/models`（多机接入不用本地文件） | **做**（复用 `codexModelsResponseFrom`，注册在 `proxy_agg.go:274` 的 mux） | 0.5 |
| `previous_response_id` | 可选（Codex HTTP 形态不用；其他 Responses 客户端会丢上下文） | 1~2 |
| 伪装 `/backend-api/codex` | **不做**（要透传 ChatGPT 登录、合并官方列表、`store=false`、错误语义） | 3~5 |
| 引入 magpie 式 IR | **不做**（aihub 是 6 条已知线路、有 `NativeResponses()` 直通；IR 的价值在「一进程接 40 家」） | — |

## 7. 需要拍板的 5 个问题

1. **新增线路能力**：A 只登记元数据、UI 标「未实现」（推荐）／B 必须绑一个已注册实现（等于再挂一条现有线路）。
2. **删除被引用的线路**：A 409 阻断、用户先清引用／B 自动连带清理并报告（推荐）。
