# 出站 TLS 指纹与客户端心跳（2026-11-05）

> 需求原话：「为了让我的aihub反代我自己的账号更加安全，现在需要你给我的aihub添加
> 【A. 加客户端心跳模拟 B. 加 TLS 指纹伪装（utls）】」
>
> 本文记录这两件事的做法、参数、验证结果与残留缺口。接口/环境变量/文件路径都可直接照着查。

## 0. 一页结论

| 项 | 实现 | 默认值 | 开关 | 验证 |
|---|---|---|---|---|
| A 客户端心跳模拟 | `hub-go/heartbeat.go` | **开**，4~9 分钟抖动，01:00~07:00 静默，日上限 120 | `AIHUB_HEARTBEAT=0` / `POST /api/heartbeat` | 单测 13 条 + 真机 intl 目录探针（23 条目）|
| B TLS 指纹伪装 | `hub-go/tlsfp.go`（uTLS v1.8.2） | 桌面端 `chrome`(133)，opencode `golang` | `AIHUB_TLS_FP=off` / 按线路 `AIHUB_TLS_FP_<LINE>` | 真机 JA3 对比：uTLS `8650db…` vs Go `03117a…`；ALPN 协商 h2 |

两件事解决的是同一判据里的两个不同维度（见 `docs/2026-10-25-封号风险与出站身份对齐.md`）：

```
上游判据 ≈ 请求指纹（头 + TLS） × system 身份句 × 请求节奏
                              ↑ B 补这块              ↑ A 补这块
```

身份头、身份句、重试放大、冷却闸门在 10-25 那轮已经做完；这轮补的是**传输层指纹**和**节奏**。

## 1. B —— 出站 TLS 指纹（uTLS）

### 1.1 问题

hub 之前用 Go 自带 `crypto/tls` 直连上游。Go 的 ClientHello 有非常稳定的形状：

```
Go 默认 JA3: 771,49195-49199-49196-49200-52393-52392-49161-49171-49162-49172-4865-4866-4867,
             0-11-65281-23-18-5-10-13-50-16-43-51,4588-4587-4589-29-23-24-25,0
```

而官方客户端是 Electron（Chromium），JA3 完全不同（扩展顺序还会抖动、带 GREASE、带 ALPS/ECH）：

```
Chrome(utls) JA3: 771,4865-4866-4867-49195-49199-49196-49200-52393-52392-49171-49172-156-157-47-53,
                  17613-18-65281-27-23-51-65037-11-43-10-35-45-5-16-0-13,4588-29-23-24,0
```

两者放在一起，不需要任何深度包检测就能区分「Go 写的代理」和「Electron 客户端」。

### 1.2 做法

只在**拨号层**替换 TLS 握手，HTTP 语义、重试、超时、流式处理全部不动：

```go
tr := &http.Transport{ /* 原有字段不变 */ }
applyTLSFingerprint(tr, line)   // Proxy 关掉 + DialTLSContext 换成 uTLS
```

`applyTLSFingerprint` 做三件事：

1. `tr.Proxy = nil`，代理判断/建隧道改由 `tlsfp.go` 自己做；
2. `tr.DialTLSContext = d.dialTLSContext`，内部用 `utls.UClient(conn, cfg, helloID)` 握手；
3. HTTP 版本按客户端画像决定（2026-11-05 晚起默认 `http/1.1`：`ForceAttemptHTTP2=false` +
   `TLSNextProto` 置空 + ALPN 收窄，理由见 `docs/2026-11-05-社区方案调研与客户端画像.md`；
   `AIHUB_HTTP2=1` 时可开回 h2，此时靠下面的 ConnectionState 适配生效）。

#### 为什么必须接管 Proxy

`net/http` 的 `DialTLSContext` **只在「非代理」路径被调用**：走代理时请求先 `t.CONNECT`，
`addTLS` 分支发现连接不是 TLS，就用 `crypto/tls` 自己握手
（`/usr/local/go/src/net/http/transport.go:1885-1920`）。
如果只装 `DialTLSContext` 而不关 `Proxy`，**所有走代理的线路（intl / oc）指纹会静默回到 Go**。
所以 `tlsfp.go` 自己实现了：

- HTTP 代理：`CONNECT target` + `Proxy-Authorization: Basic`
- HTTPS 代理：先和代理做一次标准 TLS，再 CONNECT
- SOCKS5 / socks5h：问候 → （可选）用户名密码 → CONNECT，域名交给代理解析

代理选择逻辑复用原来的 `resolveRequestProxy`（环境变量 → 探活 → 死代理回落直连 → 系统代理），
所以「代理关了自动直连」的老行为不变。

#### 为什么需要 ConnectionState 适配

`net/http` 判断「这条连接能不能跑 h2」靠类型断言
`interface{ ConnectionState() crypto/tls.ConnectionState }`
（`transport.go:1892`）。`utls.UConn.ConnectionState()` 返回的是 utls 自己那份
`ConnectionState` 类型，断言失败 → `pconn.tlsState` 为空 → h2 静默降级成 1.1。
`tlsfp.go` 里 `utlsTLSConn` 把字段搬成标准库类型后，h2 正常（实测 `resp.Proto == HTTP/2.0`）。

#### 档位表

| 线路 | 默认档 | 理由 |
|---|---|---|
| dom / intl | chrome | WorkBuddy 桌面端是 Electron |
| qoder | chrome | Qoder IDE 是 Electron |
| trae | chrome | Trae IDE 是 Electron |
| zcode | chrome | ZCode 桌面端是 Electron |
| teleagent | chrome | TeleAgent 桌面端是 Electron |
| oc | golang | 官方只有 CLI（Node/undici），硬装浏览器反而更怪 |
| mimo | chrome | 线路未打通，先按桌面端 |

档位固定（不是每次随机）：真实客户端不会每次连接换一套指纹；Chrome 档内部自带的扩展乱序
由 uTLS 的 `HelloChrome_Auto` 负责，和真 Chrome 一样。

#### 回退

uTLS 握手失败（中间设备干扰、上游只认某类扩展）时：

- 证书校验类错误**不回退**（Go 也一样过不了，重拨只会掩盖问题）；
- 其他错误回退一次 `crypto/tls`，并在 `hub.log` 记
  `[tlsfp] <line> → <host> uTLS(chrome) 握手失败，回退 Go TLS：…`；
- 统计里记 `fallbacks`，控制台可见。

关掉回退：`AIHUB_TLS_FP_FALLBACK=0`。

### 1.3 环境变量

```sh
AIHUB_TLS_FP=chrome            # 全局默认：chrome|firefox|safari|edge|golang|off
AIHUB_TLS_FP_INTL=firefox      # 按线路覆盖（线路名大写；dom/intl/qoder/trae/zcode/teleagent/oc/mimo）
AIHUB_TLS_FP_FALLBACK=0        # 关掉失败回退
AIHUB_TLS_FP_DEBUG=1           # 每次握手打一行（profile / ALPN / TLS 版本 / 代理）
```

改完要重启控制台（transport 在进程启动/线路启动时构造）。写错档位名不会静默关闭，
而是按默认档跑并打日志 —— 避免「以为开了其实没开」。

### 1.4 验证

```sh
# 真机 JA3 对比（打 tls.peet.ws，不涉及任何上游账号）
TLSFP_LIVE_TEST=1 go test -run TestLiveTLSFingerprintJA3 -v
```

实测输出（2026-11-05）：

```
utls-chrome proto=HTTP/2.0 ja3_hash=8650dbb6031fd86c484a7b1dd78319c5
go-default  proto=HTTP/2.0 ja3_hash=03117a8ed39ef02427ebbc39f121275c
指纹差异确认：utls=8650dbb6031fd86c484a7b1dd78319c5 go=03117a8ed39ef02427ebbc39f121275c
```

离线测试（不出网）覆盖：档位选择/环境覆盖、transport 接线（Proxy 关掉、h2 打开）、
本地 h2 服务真握手、HTTP CONNECT 隧道内握手、SOCKS5 无认证/用户名密码/坏密码、
代理状态码解析。见 `hub-go/tlsfp_test.go`。

### 1.5 残留缺口（如实写明）

- **HTTP/2 帧指纹**：2026-11-05 晚些的「客户端画像」改动后**默认不再协商 h2**
  （ALPN 收窄为 http/1.1，`TLSNextProto` 置空），所以「Go 的 h2 帧」这条矛盾默认不存在了。
  要开 h2 用 `AIHUB_HTTP2=1`，此时 SETTINGS/priority 仍是 Go 的形状
  （Akamai hash `b4e6bd27…`，与真 Chrome 不同）—— 见
  `docs/2026-11-05-社区方案调研与客户端画像.md`。
- **只覆盖 `crypto/tls` 出站**：本地监听（127.0.0.1:87xx/8790）仍是明文 HTTP，不涉及。
- **档位是「同族」不是「同版本」**：uTLS 提供 Chrome 133 / Firefox 120 / Safari 16 /
  Edge 85；与具体桌面端小版本不逐位相同，但 JA3 族一致。

## 2. A —— 客户端心跳模拟

### 2.1 为什么

官方桌面端在没人聊天时也不完全静默：它会周期性拉配置目录、刷积分、拉模型列表。
而反代只在你发消息时出网，形状是「长时间零流量 + 密集对话突发」——这本身就是 Bot 特征。
心跳不是为了刷额度，是为了让「节奏」这一维看起来像活人。

### 2.2 只发这四条（都是官方客户端本来就会打的只读 GET）

| 线路 | 端点 | 说明 |
|---|---|---|
| dom | `GET /v3/config` | 桌面端启动与定时刷新都打 |
| intl | `GET /v3/config` | 同上 |
| qoder | `GET /algo/api/v2/model/list` | 模型目录 |
| zcode | `GET /api/v1/client/configs` | 客户端配置 |
| teleagent | `GET /superCowork/sapi/user/portal/points/detail` | 积分 |

这些请求**只发不落盘**：心跳拉回来的目录内容不写 `wb_catalog_*.json`，也不触发
`~/.codex` 目录文件重写（那是看板/启动预热的职责）。心跳要的只是「上游看见一次
官方客户端在拉目录」，每 5 分钟重写一遍磁盘纯属多余。

**不发**（有明确理由，控制台会显示）：

| 线路 | 原因 |
|---|---|
| trae | 唯一周期动作是 `ExchangeToken`，会轮换 refreshToken，和真实对话请求抢，插进去可能把 token 弄失效 |
| oc | 匿名 public 凭据，没有「账号」可保护 |
| mimo | 线路本身没打通 |

### 2.3 参数与安全边界

| 参数 | 默认 | 环境变量 | heartbeat.json 字段 |
|---|---|---|---|
| 开关 | 开 | `AIHUB_HEARTBEAT=0` | `enabled` |
| 最小间隔 | 240s | `AIHUB_HEARTBEAT_MIN` | `min_interval_sec` |
| 最大间隔 | 540s | `AIHUB_HEARTBEAT_MAX` | `max_interval_sec` |
| 空闲闸门 | 90s | `AIHUB_HEARTBEAT_IDLE` | `idle_gate_sec` |
| 每日上限 | 120 | `AIHUB_HEARTBEAT_MAXDAY` | `max_per_day` |
| 静默开始 | 01 时 | `AIHUB_HEARTBEAT_QUIET_FROM` | `quiet_from_hour` |
| 静默结束 | 07 时 | `AIHUB_HEARTBEAT_QUIET_TO` | `quiet_to_hour` |

边界（`heartbeat.go` 顶部注释同款）：

1. **只读**：不发聊天、不签到、不动 token、不重试；
2. **抖动**：`[min,max]` 均匀随机，不是整点定时；
3. **夜间静默**：默认 01:00~07:00 一条不发，错过的也不补；
4. **空闲闸门**：该线路最近 90 秒有真实请求 → 本次跳过（官方客户端在用户活跃时不会额外轮询）；
   真实请求来自两处：`recordUsage`（聚合/opencode）与各线路监听层的 `lineActivityMiddleware`；
5. **日上限**：超了只记状态不发；
6. **失败只记账**：不重试、不放大（10-25 那次的 11128 就是重试放大器），连续失败也不会加频。

调度：每次 tick 只发**一条**，选「最久没发过」的线路；从未发过的优先。

### 2.4 落盘与接口

- 配置：`<数据根>/heartbeat.json`（0600，tmp+rename 原子写）
- `GET  /api/heartbeat` → `{ok, heartbeat:{enabled, settings, day, day_count, total_runs, last_run, next_tick, last_skip, lines[], unsupported}}`
- `POST /api/heartbeat` → 局部更新，例：`{"enabled":false,"min_interval_sec":300,"max_interval_sec":600}`
- `GET  /api/tls-fingerprint` → `{ok, tls_fingerprint:{enabled, global, fallback, lines{profile,handshakes,fallbacks,last_alpn,last_tls,last_at}}}`
- 两者也并入 `GET /api/status`（`heartbeat` / `tls_fp` 字段）
- 控制台：设置页新增「出站伪装（心跳 / TLS 指纹）」卡片，可开关心跳、看每条线路最近结果

### 2.5 验证

```sh
go test -run 'TestHeartbeat|TestPickProbe|TestAPIHeartbeat|TestStopHeartbeat' -v   # 17 条，全过
# 真机：用 intl 真实凭证跑与 heartbeatProbes 完全相同的代码路径
HEARTBEAT_LIVE_TEST=1 go test -run TestLiveHeartbeatProbeIntl -v
```

实测（2026-11-05）：

```
intl 心跳探针成功：23 个条目
intl 握手统计：profile=chrome alpn=h2 tls=TLS1.3
```

即：这条心跳同时验证了 A（探针成功）与 B（走的是 uTLS chrome 档 + h2）。

## 4. 构建注意

- **首次构建需要能拉到模块**（新增 5 个）：`GOPROXY=https://goproxy.cn,direct`。
  `scripts/build.sh` 已默认 goproxy.cn；Windows 的 `build.bat` 若在内网/离线环境，
  先在有网机器 `go mod download` 再把 `%GOPATH%\pkg\mod` 带过去。
- `go build -trimpath -ldflags "-s -w" -o bin/aihub .`：`-s -w` 后约 11.7 MB，未裁剪约 16.6 MB。
- 控制台页面是 `//go:embed` 进二进制的，改 `assets/console.html` 必须重新编译。

## 5. 回滚

| 想关掉什么 | 做法 |
|---|---|
| 只关 TLS 指纹 | `AIHUB_TLS_FP=off` 后重启 |
| 只关心跳 | `AIHUB_HEARTBEAT=0` 后重启（或控制台设置页点「关闭」） |
| 全回滚 | `git revert` 本次提交；`go.mod` 的 utls 依赖可留可删 |
