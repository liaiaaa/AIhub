# 客户端出站抓包（2026-11-05）

目的：确认官方国内版 WorkBuddy 桌面端**到底用 h2 还是 HTTP/1.1**，好决定 aihub 出站该不该开 h2。
用户同意「抓一次」。

## 方法

无 root（不能 tcpdump），所以用客户端自带的两种可观测面：

1. **Chromium NetLog**：`./run.sh --log-net-log=netlog.json --net-log-capture-mode=Everything`
   —— 覆盖渲染进程 + 主进程里走 Chromium 网络栈的请求（更新检查、私有配置等）。
2. **代码核对**：`app.asar` 里对话链路的实现（`main/daemon-bootstrap.js`、`cli/dist/codebuddy-headless.js`）。

另外验证了客户端**遵守 `SSLKEYLOGFILE`**（启动时生成了 3.7 KB 的 `keys.log`）——将来若拿到
报文（有 root 的机器上 tcpdump），可以直接解密。

## 结果

### 1. Chromium 侧：TLS 1.3 + ALPN h2

NetLog 里的握手参数（3 次，全部一致）：

```json
{"cipher_suite":4866,"key_exchange_group":29,"next_proto":"h2",
 "version":"TLS 1.3","is_resumed":false,"encrypted_client_hello":false}
```

- `4866 = 0x1302` = `TLS_AES_256_GCM_SHA384`
- `key_exchange_group 29` = X25519
- 命中的 URL：`/v2/update`（检查更新）、`/v2/as/users/private-configs/query`、
  static/telemetry/COS 等**辅助**请求 —— **没有一条是对话接口**。

### 2. 对话不走 Chromium

`netlog.json` 里搜不到 `/v2/chat/completions`、`/conversation`、`acp` 任何一条。
对话链路的实现分别是：

- `main/daemon-bootstrap.js`：本机 daemon 把 VLM 请求转发到网关，用的是 Node `http(s)`
  （`res.once("finish")` + `readable.pipe(res)`），默认上游 `https://copilot.tencent.com/v2/chat/completions`；
- `cli/dist/codebuddy-headless.js`：`fetch(` 29 处、`undici` 2 处 → Node fetch/undici。

Node 的 `http`/`undici.fetch` **都是 HTTP/1.1**（Node 没有内建 h2 客户端，`http2` 模块未被这条链路使用）。

## 结论

| 流量 | 协议 | 依据 |
|---|---|---|
| 渲染进程辅助请求（更新、配置、静态资源） | **h2**（TLS1.3） | NetLog `next_proto:"h2"` |
| 对话 / 网关请求（真正需要注意的那条） | **HTTP/1.1** | 不在 NetLog 中 + daemon/CLI 走 Node http/fetch |

所以 aihub 现在「chrome uTLS + ALPN 只报 http/1.1」的选择是**对的方向**：如果按「客户端用 h2」
盲目开 h2，反而会让对话路径带上 Go 的 h2 帧指纹，比不开更矛盾。

## 没能做到的

- **没有逐字节抓对话请求**：本想用 `--proxy-server` 让客户端走本地 CONNECT 代理，但客户端没理会
  （它按自己的 system-proxy 设置走；`--proxy-server` 对 daemon 子进程无效）。
- **GUI 输入没打通**：这个窗口不接受 AT-SPI 文本注入，XTEST 焦点也被 WM 拒绝，所以没能实际发一条
  对话来让 NetLog 出现 chat 请求。上表「对话 = h1」是代码 + NetLog 缺席 + hub 同 token 走 h1 实测成功
  （`domProbeInfer result=0`）三条合起来的结论，**不是**抓包直证。
