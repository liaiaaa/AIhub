### 1.1 traework2api-panel 的结论（可直接抄的部分）

**① TLS 用「抓包复刻的 spec」，不是浏览器预置档**

`internal/upstream/tls.go` 顶部注释直接对比：

```
crypto/tls        JA3 = 771,49195-49199-…,0-11-65281-23-18-5-10-13-50-43-51,4587,0
utls Chrome_133   JA3 = 771,43690-4865-…,10794-35-23-13-65037-5-43-27-16-17613-51-45-11-18-65281-0-10-27242,4588,0
```

它默认用 `aha`（官方客户端自己的客户端形状），`chrome_133/131/120/go` 只作备选。
本仓没有 Trae 的 ClientHello 抓包，只有 HTTP 层的身份抓包，所以仍用 chrome 档；
**但这条提醒了一个事实：chrome 只是「像浏览器」，不是「像这个客户端」**。

**② 真禁 h2 的写法（重要）**

`internal/upstream/wire.go`：

```go
base.TLSNextProto = map[string]func(string, *tls.Conn) http.RoundTripper{}
```

配 `alpnForWire() []string { return []string{"http/1.1"} }`，理由写在注释里：
客户端抓包是 **HTTP/1.1 + Connection: keep-alive**；若协商到 h2 却发 h1 报文，直接坏。
代价它也承认：JA4 的 ALPN 段与真浏览器不同，是「能跑」与「完全一致」的取舍。

**③ 有状态扩展不能跨连接复用**

`specWithALPN` 每次克隆 spec，并重建 `UtlsGREASEExtension` / `UtlsPaddingExtension` /
`KeyShareExtension`（KeyShare 的 `Data` 留空，让 utls 现生成），否则多连接共用会随机
`tls: internal error`。

**④ 头名大小写与 Accept-Encoding**

`headers.go`：客户端多数头是小写、少数首字母大写；`Connection: keep-alive`；
`Accept-Encoding: gzip, deflate, br, zstd` 并自实现解压。它还记录了「发 x-request-pin
但 body 是明文 → 400 base64 decode failed」这种「头齐了反而错」的坑。

### 1.2 workbuddy2api-panel 的结论

`internal/upstream/transport.go` 注释给出**实证**：

```
ForceAttemptHTTP2=false 只对自定义 Dial 生效，默认 TLS 经 ALPN 仍协商出 h2，
半死 h2 流复用表现为 "http2: timeout awaiting response headers"——
唯一正确写法是置空映射，让 ALPN 完成后无 h2 协议可用，连接退回 HTTP/1.1。
```

连接参数：dial 10s / keepalive 15s / TLS 握手 10s / idle 30s / ResponseHeader 60s。
（本仓的对应值：dial 15s / keepalive 30s / 握手 15s / idle 90s / ResponseHeader 各线路自定。）

### 1.3 qoder2api-hub 的结论

`qoder_fingerprint.py`：**按 uid + salt 稳定派生** machineId / sessionId（UUIDv4 带连字符，
版本位固定 4、变体位固定 a），request id 每请求随机 32 hex。理由写得很好：

> 官方客户端「一个进程 = 一台设备」，而网关是一个长驻进程同时冒充几十台设备。
> 照官方那样在进程维度取一次，等于让所有账号共用同一个值，反而把它们关联到同一台机器上。

本仓 Qoder 线路本来就是按账号派生（`qoderIdentityPresets`），方向一致，无需改。

### 1.4 没采纳的社区做法（说明原因）

| 做法 | 出处 | 为什么没抄 |
|---|---|---|
| 手工复刻 ClientHello spec | traework2api | 需要真客户端抓包样本；本仓没有 TLS 层抓包，硬编 spec 风险更大 |
| 头名大小写重写（`headerCaseTransport`） | traework2api | 改动面覆盖所有线路的所有请求，收益（精确比对类规则）未验证；先记 TODO |
| 自实现 br/zstd 解压 | traework2api | 只在显式发 `Accept-Encoding` 时才需要；本仓尚未显式发 |
| 用 Python 网关那套 scheduler | qoder2api-hub | 本仓心跳调度已经覆盖同样语义（抖动/静默/日上限/空闲闸门） |

## 二、我们改成了什么

### 2.1 单表驱动：`client_profile.go`

一条线路「装成谁」现在由一张表定义，四个维度不再各写一套：

| 线路 | 客户端 | TLS 档 | HTTP 版本 | 心跳 | 心跳节奏 |
|---|---|---|---|---|---|
| dom | WorkBuddy | chrome | HTTP/1.1 | 有 | 240~540s，01~07 静默 |
| intl | WorkBuddy AI | chrome | HTTP/1.1 | 有 | 240~540s，01~07 静默 |
| qoder | Qoder | chrome | HTTP/1.1 | 有 | 300~600s，02~07 静默 |
| trae | Trae | chrome | HTTP/1.1 | **无** | —（token 轮换会和真实请求抢） |
| zcode | Zcode | chrome | HTTP/1.1 | 有 | 300~600s，02~07 静默 |
| teleagent | TeleAgent | chrome | HTTP/1.1 | 有 | 240~480s，02~07 静默 |
| oc | opencode | golang | HTTP/1.1 | 无 | —（官方只有 CLI） |
| mimo | MiClaw | chrome | HTTP/1.1 | 无 | —（线路未打通） |

身份（UA / 版本 / 桌面端）仍由 `line_identity.go` 单点定义，画像只引用不复制；
`client_profile_test.go` 遍历 `lineSpecs` 断言「每条线路都登记了画像」「桌面端必须 chrome」
「CLI 不许装浏览器」，新增线路忘登记会直接红。

### 2.2 h2 默认关（可开）

`applyTLSFingerprint` 现在按画像决定：

```go
tr.ForceAttemptHTTP2 = d.h2
if !d.h2 {
    tr.TLSNextProto = map[string]func(string, *tls.Conn) http.RoundTripper{}
}
```

h2=false 时还会把 ClientHello 的 ALPN 收窄成只有 `http/1.1`（`tlsFPSpecWithALPN`）。
开回来：`AIHUB_HTTP2=1`（全局）或 `AIHUB_HTTP2_INTL=1`（按线路）。

### 2.3 心跳节奏按线路

调度器现在用「上一条发过的线路」的画像节奏算下一次间隔：

```go
delay := heartbeatDelayForLine(cfg, lastProbeLine)
```

优先级：环境变量显式设置（`AIHUB_HEARTBEAT_MIN/MAX`） > 线路画像 > 全局默认。
这样 WorkBuddy 是 4~9 分钟、Qoder 是 5~10 分钟，而不是所有线路一个节拍。

### 2.4 踩过的三个坑（都写进代码注释了）

1. **`utls.UTLSIdToSpec` + 重建有状态扩展 = 坏包**：服务端回 `tls: error decoding message`。
   正解：ID 档位每次调用返回的就是新对象，**不要重建**。
2. **`cfg.NextProtos` 与 spec 的 ALPN 必须一致**：utls 的协商判定读 `cfg.NextProtos`，
   只改 spec 会出现「字节里报了 http/1.1、判定表还是空」。
3. **spec 里没有 PSK 扩展 + 开着 session cache = panic**：
   `tls: initPskExt failed: ... no pre-shared key extension`。
   正解：`PreferSkipResumptionOnNilExtension: true`（缺扩展时安静跳过续用）。

### 2.5 验证

```
# 单测（离线）
go test -run 'TestClientProfile|TestHeartbeatDelay|TestTLSFP|TestUTLS' -count=1
# 真机：intl 心跳探针（只读）
HEARTBEAT_LIVE_TEST=1 go test -run TestLiveHeartbeatProbeIntl -v
```

实测输出（2026-11-05 14:25）：

```
intl 心跳探针成功：23 个条目
intl 握手统计：profile=chrome alpn=http/1.1 tls=TLS1.3
```

即：uTLS chrome 档、TLS1.3、ALPN 协商为 http/1.1、真实上游返回 23 条目录。

### 2.6 下一步（可选）

- 如果能拿到某条线路的 TLS 层抓包（ClientHello 原始字节），把 `aha` 式自定义 spec 补上，
  从「像浏览器」升级成「像这个客户端」。
- 头名大小写重写（`Connection` / `Sec-Fetch-*` 等）按 `headerCaseTransport` 的思路做，
  需要先确认 Go 侧的 Header 读取路径不受影响（社区那套是 Clone 副本改 key）。
- HTTP/2 帧指纹：只有在我们决定「开 h2」时才值得做（SETTINGS/priority 顺序），
  否则默认 h1 已经绕开这个矛盾。

## 三、本机安装包实证（2026-11-05，`/home/<user>/opt/workbuddy/workbuddy_dom`）

用户提供了国内版 WorkBuddy 桌面端的本地安装目录，直接读安装包比「按社区文档猜」硬：

| 事实 | 出处 |
|---|---|
| 版本 **5.6.2**（build `c7b525f…`），Electron **37.10.3** | `data/last-launch.json`、`app/version` |
| 官方 endpoint 是 **https://www.workbuddy.cn**；`copilot.tencent.com` 只是 officialEndpoints 里的历史候选 | `app/resources/app.asar.unpacked/cli/product.json` |
| UA 形状：`WorkBuddy/<ver> WorkBuddy/<ver>` + 可选 ` CLI/<ver>`（版本段**重复两次**） | `main/daemon-bootstrap.js` 的 `buildComputerUseVlmGatewayHeaders` |
| 身份头：`X-IDE-Type/Name=WorkBuddy`、`X-IDE-Version`、`X-Private-Data`、`X-Product`、`X-Domain`；有 uid 时带 `X-User-Id`，企业号再加 `X-Enterprise-Id`/`X-Tenant-Id` | 同上 |
| 网关头：`x-requested-with: XMLHttpRequest`、`X-Conversation-*`、`X-Agent-Intent/Purpose`、`x-codebuddy-request: 1`、trace 三件套（traceparent / b3 / X-Trace-ID，共享同一个 traceId） | `applyGatewayHeaders` |
| **`X-Device-Token` 来自腾讯 TuringShield SDK 原生库**；`native/turing-sdk/index.cjs` 里 `supportedPlatform = darwin || win32`，Linux 直接 `binding = null` | `native/turing-sdk/index.cjs` |

由此落地的两件事：

1. **dom 默认 base 从 `copilot.tencent.com` 切成 `https://www.workbuddy.cn`**（`wbCNBase()`），
   依据就是官方客户端自己的 product.json；旧域用 `AIHUB_WB_CN_BASE` 可回退。
   真机验证：`dom 心跳探针成功：34 个条目（backend=https://www.workbuddy.cn）`。
2. **X-Device-Token 这条不算我们的缺口**：Turing SDK 只支持 macOS/Windows，本机 Linux 版
   官方客户端同样拿不到 token（`fetchDeviceToken` 直接抛 `unsupported platform linux`，
   客户端改为发 `X-Device-Token-Error`）。也就是说「Linux 上没有这个头」与官方行为一致。

> 注意：本地客户端版本 5.6.2 比我们 UA 里的 5.8.3 旧。5.8.3 来自另一份 macOS 安装包抓包
> （`docs/2026-10-21-dom渠道校验.md`），两者都是真实存在的版本；UA 保持 5.8.3 不动，
> 因为上游若校验「版本是否在支持区间」，更新的值更安全。

**账号状态实测（重要）**：dom 账号当前已被上游 **11140 账号级风控**
（`request illegal` / `account has been restricted due to unusual activity`），
对话接口 403；目录与 billing 仍 200。这不是请求头的问题，换号或等风控解除才是解法。

## 四、桌面端实时凭据同步（2026-11-05 追加）

用户指出「aihub 本来就有解密 WorkBuddy 的东西」——对，`workbuddy_atrest.go` 早就能用
`wbatrest.key` 解 `$wbEncrypted` 信封。问题不在解密能力，而在**读的是哪份文件**：

- `国内workbuddy凭证/workbuddy-desktop.info` 是 2026-10-08 手工导出的一份副本，
  JWT 是 `azp=console` 的控制台身份 → `/v3/config` 能用，`/v2/chat/completions`
  一律 **401（openresty/APISIX）**，刷新也回 `invalid_grant: Session doesn't have required client`。
- 官方 Linux 客户端把**实时**凭据写在
  `~/.local/share/CodeBuddyExtension/Data/Public/auth/workbuddy-desktop.info`
  （mtime 2026-11-05 13:32，`expiresAt` 2026-12-05，同一 uid）。
  用 hub 现有的解封代码直接读它，探活 **result=0（成功）**。

于是新增 `hub-go/dom_live_cred.go`：读取前做「只读同步」——桌面端文件比 hub 副本新，
就原子覆盖副本（先校验能解封、是完整 JSON、有 `auth` 字段）。hub 自己刷新仍写副本，
不碰桌面端文件；桌面端下次刷新再覆盖回来。

```
AIHUB_WB_LIVE_CRED=/path/to/workbuddy-desktop.info   # 覆盖源；off 关闭
AIHUB_WB_LIVE_DEST=/dir 或 /dir/xxx.info            # 覆盖副本位置
```

只对「副本路径」生效：其它凭证目录 等其它账号目录不会被同一个登录态覆盖。

实测：同步后副本变成 9930 字节（桌面端那份），`domProbeInfer` 返回 `result=0`。
