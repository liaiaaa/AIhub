## 1. 硬约束：这个进程正在给 Codex 供流

用户当前这个 Codex 会话的模型 provider 指向 **`http://127.0.0.1:8790/v1`**
（见 `~/.codex/config.toml` 的 `[model_providers.aihub]`，`wire_api = "responses"`）。
也就是说：

- **重启 hub = 当前会话当场断流。**
- 因此本会话全程遵守：**不覆盖 `hub-go/bin/aihub`、不动 systemd unit、不用默认
  8801 端口起第二实例**。

| 单元测试 | `go test -count=1 -short ./...` | 不会（测试用 `127.0.0.1:0`/`18796` 等错开端口，`usage_stats_test` 用 `t.TempDir()` 隔离数据根） |

## 4. 那个 bug：聚合卡片「模型下拉」不刷新（已修，待重启生效）

### 现象（用户原话）

> 当我点击 8790 的启动聚合后，下面模型显示的位置那边还是会显示当前聚合未开启 xxx，
> 然后当我刷新一次页面后就恢复正常显示正常的模型了

### 定位过程

页面源码里**搜不到「未开启」这三个字**，所以先把它抓成实物：用 headless Chrome
加载真实页面，读到那个位置的实际文案是 **「线路未启动，请先在上方启动它」**
—— 位置是 `#agg-model` 那个 `<select>`，即「选好线路 → 添加模型」的下拉框。

### 根因

`webui.go` 里 `#agg-model` 只在**页面加载**和**切换线路**时取过一次
`/api/agg/line_models`，而该接口的答案随线路启停变化（线路没起来时只回一句提示）。
之后 2 秒一次的状态轮询只更新圆点和模型数，**从不重取这个下拉**，
于是它一直停在「打开页面那一刻」的结论上。刷新页面 = 重新取一次 = 恢复正常。
和聚合口本身启没启动无关，是纯前端缓存问题。

### 修法（`8433bac`，`webui.go` 内嵌 JS，+27/-1 行）

- `renderAgg()` 里记住上次取数时的签名 `线路|该线路是否在跑`，轮询发现翻转就补拉。
- **刻意只在翻转时补拉**，不是每轮都拉：否则线路没起来时会每 2 秒重试，
  下拉反复闪「加载中…」。
- 顺带修两处同源小问题：重取时保住用户已选中的模型；加序号丢弃过期响应
  （避免快速切线路时旧结果覆盖新结果）。

### 验证方式（可复现，且不碰线上）

```bash
python3 hub-go/scripts/webui-check/stub.py 8899   # 终端 1
node    hub-go/scripts/webui-check/verify.js      # 终端 2
```

`stub.py` 把 `/api/*` 换成可编程假数据（`/ctl?intl=1` 可置线路启停），
页面本身从 `webui.go` 里抽真货。**9 项断言全过**；把 webui 换回修复前的版本
再跑，会失败 3 项（含用户报的那一项）—— 所以这套断言是真的有效。

## 4.1 图片被翻译层丢掉（已修，待重启生效）

### 现象

Codex 走聚合口 `:8790`（`wire_api = "responses"`）发截图提问，模型答
「没有收到图片」，然后开始瞎猜、反复找错文件。用户描述的「看不清楚」和
「反复找错」是**同一个 bug 的两个症状**。

### 根因

`proxy_responses.go` 的 `responsesContentText` 只认文本片段，Codex 传图用的
`{"type":"input_image","image_url":"data:image/png;base64,..."}` 没有对应
`case`，被静默跳过。更糟的是纯图片消息在 `responsesInputToMessages` 里因
「文本 trim 后为空」被整条 `continue` 掉——**模型收到的是一条没有图的空消息**。

聚合口同样中招：`proxy_agg.go` 的 `responsesBodyToChatBody` 复用的就是同一个函数。

> 注意：`hub-go` **自己没声明** `input_modalities`，那是 Codex 客户端默认加的，
> 所以 Codex 会正常把图附上——「发是发出去了，中间被吃了」。

### 实测证据（同一张图、同一上游）

| 发给上游的形态 | 模型回答 |
|---|---|
| 直发 chat 格式含 `image_url` | `"白色"`，思考链里描述出「红色背景，中间一个白色正方形」 |
| 经聚合口 Responses 路径（修复前） | `"没有收到图片，无法判断"` |

复现用的自造图：`/tmp/vision_test.png`（64×64 红底 + 白色方块，144 字节）。

### 修法（`722e29d`，`proxy_responses.go` +140/-4）

- `responsesContentChat`：纯文本仍返回 `string`（形态不变，绝大多数请求走这条）；
  含图时返回 chat 协议的 parts 数组，text/image_url 交替、顺序保持。图片片段
  同时接受 Responses 的 `{"image_url":"data:..."}` 与 chat 的
  `{"image_url":{"url":...}}` 两种形态。
- `isEmptyChatContent`：数组只看 `len>0`，**纯图片消息不再被丢**。
- `sanitizeHarnessPromptAny`：`developer/system` 降敏能穿过 parts 数组，
  只改文本、图片原样保留（原 `sanitizeHarnessPrompt` 只吃 `string`）。
- `chatImageDetail`：上游不认 `original`，统一退到 `high`；显式
  `low/medium/high` 尊重客户端。顶层片段与嵌套 `image_url` 两处都能取到。

测试：`proxy_responses_vision_test.go` 8 项断言（纯图片消息必须留下、空消息仍
剔除、text→image→text 顺序、降敏不丢图、original 退档、全链路仍带图）。

### 还没做：分辨率

`proxy_responses.go:75` 的 `"supports_image_detail_original": false` 会让 Codex
发图前先缩放（长边约 1568px），密集小字截图缩完会糊。想试原图就改 `true`，
但要先确认上游真能吃——**不确定就先保持 `false`**，等主修上线后看实际效果再定。

### 若修完仍不理想

那就是模型侧的事，按性价比排序：
1. 别指望 flash 读密集小字。让模型改走「跑命令把报错抓成文本」（`grep`/读日志）
   通常比修视觉省事。
2. 同一张图换模型对比：`dom.glm-5.3-flash`、`qoder.Qwen3.8-Flash` 都在同一套
   翻译层后面，修完主 bug 后能立刻区分「管道问题」还是「模型问题」。
3. 需要的话可在 hub-go 加图片预处理（放大+提对比度+可选 OCR 把文字一起塞进
   prompt），纯工程活，通常比换模型立竿见影。

## 4.2 图片在**工具结果**里被丢掉（第二次修复，已修，待重启生效）

### 现象（用户原话）

> 为什么在 dsh 中我使用 deepseek 4.1 flash 国际的这个模型，识别图片的功能很好啊，
> 同一张图片，同一个模型，使用 dsh 可以找到投递邮箱，使用 codex 却找不到邮箱，
> 然后还胡扯，这是为什么？

用户实际对照（10-12 晚）：同一张芯灵光子招聘海报，
**DSH 读出 `zhouyuxian@opteryx.com.cn`，Codex 读不到还反复找错图。**

### 根因：图片根本不在用户消息里，而在**工具结果**里

`722e29d` 只修了「图片在用户消息里」。但 Codex 看图的真实路径是 **`view_image` 工具**：

```
用户消息：<image name=[Image #1] path="/tmp/codex-clipboard-xxx.png">
模型调用：view_image(path=...)
工具结果：function_call_output.output = [{"type":"input_image","image_url":"data:image/png;base64,..."}]
```

而 `proxy_responses.go` 的 `function_call_output` 分支走的是
`responsesItemOutput` → `responsesContentText`（**只认文本**）→ 图片被静默丢弃 →
工具结果变成**空字符串**。

模型看到的是「view_image 返回了空结果」，于是回一句
**「工具没有返回任何图像内容，我看不到」**，再凭文件名/上下文瞎猜 —— 这就是用户说的「胡扯」。

**DSH 为什么没这个问题**：它走 chat 协议直发 `:8799`（`api: openai-completions`），
工具消息里的 `image_url` 原样保留，压根不经过 Responses 翻译层。
→ 所以这不是模型能力差异，是**只有 Codex 这条路经过的翻译层在吃图**。

### 实测证据（`:8790` 真实请求，同一张自造 64×64 纯红 PNG）

| 图片位置 | 修复前 | 修复后 |
|---|---|---|
| 用户消息里 | 「红色」 | 「红色」 |
| **工具结果里** | **「工具这次没有返回任何图像内容，我看不到」** | **「红色」** |

把改动回退成 `responsesContentText` 再跑，第二行立刻复现原症状（负向对照已验证）。

上游能力单独验证过：`role=tool` 的 `content` 用 parts 数组带 `image_url`，
`:8799` 返回 HTTP 200 并答出主色 —— **不是上游不收，是本层没发**。

### 修法（`b6c2916`，`proxy_responses.go`）

- 新增 `responsesItemOutputChat`：纯文本仍返回 `string`（绝大多数工具结果走这条，
  形态不变）；含图时返回 chat 的 parts 数组，`text`/`image_url` 交替；纯图片
  （截图类工具只回图）也保留；既无文本又无有效 URL 时退回空串，不把 `null`/空数组
  塞给上游触发参数校验错误。
- `function_call_output` 分支改用它。
- `responsesContentText` 补注释：只用于「确定只要文本」的场合，别再拿它处理可能含图的 content。

### 验证方式

```bash
cd hub-go
go test -run 'ItemOutput|ToolImage|Image' -v .          # 离线断言，含负向对照所需用例
INTL_LIVE_TEST=1 go test -run TestLiveToolResultImage -v .   # 真实上游端到端（自动跳过 11140 风控凭证）
```

`proxy_responses_vision_live_test.go` 会自己造纯色 PNG、起临时端口、
逐个凭证探测（11140 是账号级风控，与内容无关，命中就换下一个），
**不影响正在运行的 hub**（不碰 8790/8799/8801）。

> 教训（值得记住）：排查「模型看不到图」时，**先确认图在哪一段消息里**。
> Codex 附图和 Codex 的 `view_image` 工具结果是**两条不同的翻译路径**，
> 修了一条不代表另一条通。
